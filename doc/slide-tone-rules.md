# スライドの語り口ルール — 素の教室の言葉

対象：本リポジトリの全デッキ。例の → の左が修正前、右が修正後。

**原則：情報はそのまま、演出だけを削る。** クイズ番組・手品・ゲームの語り口に寄せない。素の教室の言葉で言い切る。

## 1. 語彙 — ゲーム・ドラマの言葉を使わない

| 修正前 | 修正後 |
|---|---|
| クイズ（callout タイトル・見出し） | 質問 |
| 種明かし（callout タイトル） | 答え |
| 種明かし：〜（地の文） | 実は、〜 |
| 線と木で**遊ぶ** | 線と木を**少し変える** |
| 自分の縦線でスライドに**勝負** | 自分の縦線でよりよい閾値をさがせ |
| **金庫にしまっておいた**テストデータ | テストデータ |
| ラベルを**失った**魚たち | ラベルの**ない**魚たち |

- 「クイズ」が許されるのは、文字どおりのクイズアプリを指すときだけ（最終課題のジャンル表など）。
- 設計ドキュメント側での装置名は「問いかけ→めくり」（[engaging-lecture-design.md](engaging-lecture-design.md) 準拠）。

## 2. 見出し・callout タイトルは機能ラベル

使う語彙：**質問／答え／今回の主題／要するに／ここまでで分かること／結果／チェックポイント／重要ポイント**

- 「ここで観察」→「結果」「チェックポイント」、「発見」→「ここまでで分かること」、「今回の問い」→「今回の主題」。
- 疑問形タイトルは、本当にその回の動機づけの問いのときだけ（例：「特徴量の数を増やすのが最強か？」）。それ以外は内容を言い切る（「あやしい満点」→「学習データでの満点は意味がない」）。
- 直後にめくりが来るなら、問いの形を取らず平叙文で断言してよい（「クイズ：直線1本で分けられる？」→「単純に考えると：直線では分離不可能」）。
- Tweak 表の行は学生への指示形・疑問形（「〜をさがせ」「〜せよ」「満点が出る深さはどこ？」）。名詞句の目標列挙にしない。

## 3. 章区切りスライド（break-slide）は裸のトピック名だけ

- 「発展：決定木を手で作る」→「決定木」、「授業内コアへ戻る：PCAを使う」→「PCAを使う」。
- 「発展：」「授業内コアへ戻る：」のようなコース構造のナビゲーションはメタ発言なので書かない。位置づけは構成（配置・（参考）マーク）で示す。

## 4. コードネーム禁止・比喩は技術用語とセット

- 概念に愛称（コードネーム）を付けて別スライドから参照しない。リンクテキスト「あやしい満点」→「スライド」＋素の説明、「暗記の境界に」→「境界に」。
- 比喩そのものは残してよいが、必ず技術用語を添える：「『暗記』がもたらす弊害（**過学習**）」、callout「This is 過学習」。
- 比喩の再アンカー規則（回をまたぐときは回名/glossを付ける）は従来どおり。

## 5. 鮮やかさより正確さ

- 「境界を下げる」→「**決定境界の閾値**を下げる」。用語は省略せず正確に。
- 「垂線」→「縦軸に平行な直線」。数学用語の誤用・曖昧用は避ける。
- 装置名は事実に合わせる：「人感センサ」→「輝度センサ（人感ライトみたいな簡単なやつ）」。カジュアルな補足は括弧内なら可。
- 詰めた複合語を作らない：「3山」→「3つの山」、「青破線」→「青の破線」。

## 6. 構成

- **節を「 — 」（ダッシュ）でつながない**。「決定木・k-means・PCA — 手法は変わっても…」のような連結はやめ、文を「。」で分ける／「：」で導入する／入れ子の箇条書きに割る。
- **「AがX、BがY」の「、」並列も箇条書きに割る**。例：「物差しが**損失関数**、探す手段が**最適化**。」→ 損失関数と最適化を1項目ずつの箇条書きに。
- 本筋のウォークスルーコードは `code-fold: false`（折り畳まない）。
- 図・出力の後の考察は callout に入れる（タイトル「要するに」等）。裸の箇条書きを図の下にぶら下げない。
- 道具の定義が先、内部基準は後（「決定木とは」→ そのあとで「ジニ不純度」）。
- 1行に事実を詰め込まない：本文は箇条書きに分解、`print` は1行1事実。
- **箇条書きの項目に「。」で文を2つ並べない**。1項目＝1文で句点なし。2つ目の文は字下げした子項目にする。
   - 例：「最良は 5.0。Tweak で見つけた値と同じ」→「最良は 5.0」＋子項目「Tweak で見つけた値と同じ」
   - 短い補足なら「（…）」で同じ行に添えてよい。
- 式や図に添える1行の注釈は箇条書きにしない。`.caption-note` で直下に添える。
- **コードの前の箇条書きは手順だけを書く**。何をどの順にやるかを書き、関数名・引数はコードに任せる。前のスライドと同じ操作なら「〜と同様に」でつなぎ、コードも前のスライドと同じ形で書く。
   - 例：「魚の番号 0〜119 を `np.arange` で作り、`np.random.shuffle` でランダムに並べ替える」→「まずデータをランダムに並べ替える」「次に「どうやって分ける？」と同様にスライスする」
- **見出しと箇条書きで全部を説明しない**。見出しは場面を短く言う。モデルや指標はコードに任せる。結果から何が言えるかは、直後に議論のスライドを立ててそこで論じる。
   - 見出し：「前回と同じ採点方法」→「全データで学習してしまったとしたら」
   - コードの前の「モデルは〜」「成績は〜」の箇条書きは削除（コードを見れば分かる）
   - 結果の callout は「またしても満点」だけ残す
   - 「この値だけでは分からない」「データを分ける」は、断言の見出しを付けた議論のスライド「すべてのデータで学習するという発想が誤り」で論じる。結果の callout の末尾や、次の手順のスライド（「どうやって分ける？」）に押し込まない
   - 冒頭の「今回の主題」と同じ問いを、途中の「質問」callout で繰り返さない
- **手順の正しさを自分で褒める行を書かない**。「テストデータは、この最後の採点以外に一度も使っていない」「深さは、訓練データ内の交差検証だけで決まった」のような callout・箇条書き・コードコメント（`# テストデータを使うのはここだけ`）は削除する。正しい手順はスライドの流れとコードで見せる。
- **1文に修飾を積まない。何があるかを先に短く言い、詳細は子項目に割る**。「本編の〜と比べて」のような前置きも不要。
   - 「scikit-learn の `train_test_split` は、本編の並べ替えと切り分けを1回の呼び出しで行う」→「訓練データとテストデータの分離をしてくれる関数がscikit-learnにある」＋子項目 `train_test_split`、その下に引数・返り値
- 見出しは考え方を書き、実装の都合を入れない（「番号をランダムに並べ替えてから分ける」→「ランダムに並べ替えてから分ける」）。
- 状態を変える操作の前後を `print` で並べて見せるのは、大抵しない。やりすぎるとコードが長くなる。変化そのものがスライドの要点のときだけ使う（例：`shuffle` の前後の `idx[:10]`）。
